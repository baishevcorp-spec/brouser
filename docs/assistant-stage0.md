## 1. Реестр тулов (имя — одна строка)

Каждый тул = обёртка над СУЩЕСТВУЮЩИМ методом ProfileManager/Logger: ноль
новых привилегий в main, ноль новых IPC-каналов. Параметры и ответы —
строго типизированы (Zod, этап 2); ответ тулa ≤ 4–8 КБ.

### Управление сеткой и ячейками

| # | Тул | Что делает (одна строка) |
|---|---|---|
| 1 | `list_profiles` | Список профилей: имя, URL, видимость (ячейка/парковка), флаги прокси-схемы/UA/таймзоны, число расширений и их статус. |
| 2 | `profile_details` | Сводка одного профиля: расширения со статусами загрузки, локаль/гео/seed, настройка ротации прокси (интервал, есть ли URL) — без учётных данных. |
| 3 | `grid_info` | Текущая раскладка, число ячеек, счётчик профилей/видимых, состояние синхронизатора действий. |

| 6 | `reload_all` | Перезагрузить страницы во всех видимых ячейках. |
| 7 | `open_devtools` | Открыть DevTools профиля в отдельном окне (с корректным CDP-dance P2.1). |
| 8 | `reorder_profile` | Переставить профиль в другую ячейку (механика drag-and-drop: сдвиг в config.profiles, views переносятся). |
| 9 | `toggle_input_sync` | Включить/выключить синхронизатор действий (реплей кликов/ввода между ячейками). |

## 2. Разрешение профиля (Zero-Trust, ТЗ)

Модель НЕ передаёт profileId — main подставляет профиль сам. Порядок
разрешения аргумента `profile` (строка):

1. точное совпадение `id` в config.profiles;
2. уникальное совпадение по `name` (регистронезависимо; неоднозначность →
   error с подсказкой «уточните имя»);
3. `active` (слово-псевдоним «этот/текущий профиль») → профиль выбранной
   в сетке ячейки;
4. промах → `{ok:false, reason:"профиль не найден"}` — модель сообщает
   пользователю, без попыток угадать.

**Новая зависимость (не существовала):** «выбранный профиль» живёт только в
renderer (`selectedId` в renderer.ts) — main о нём не знает. Для пункта 3
нужен крошечный IPC `ui:selected-profile` (renderer → main, ~10 строк) —
добавится на этапе 1.

## 4. Архитектурные развилки (решение — за пользователем)

### Развилка 1: где живёт панель ассистента

- **(A) Встроенная панель справа в главном окне + резервация места в layout**
  (как панель журнала: `logPanelReserve` в layout.ts, IPC `ui:log-panel`).
  Панель всегда рядом с сеткой, не перекрывается views, сворачивается.
  ~30–40 строк в layout.ts (резерв под обе панели сразу: журнал ИЛИ ассистент,
  одновременно — сумма, ограничим: вторая панель заменяет первую).
- **(B) Отдельное BrowserWindow** (как «Настройки»): проще, ноль правок
  layout — но это «пульт в другом окне», а не панель у сетки.

**Рекомендация: (A)** — весь смысл ассистента «пульт рядом с сеткой»;
механика резерва уже отработана журналом. Если хотите минимальный риск — (B).

### Развилка 2: где настройки ассистента (Cloud/Local/Auto, ключ, голос)

- **(A) Новый раздел в существующем окне «Настройки»** — одно окно настроек.
- **(B) Отдельное окно настроек ассистента.**

**Рекомендация: (A).**

### Развилка 3: модель Ollama Cloud с надёжным tool calling

- **(A) `gpt-oss:20b`** — нативный tool calling, быстрый, экономный.
- **(B) `qwen3:32b`** — длинный контекст, стабильный формат вызовов.

**Рекомендация: (A) `gpt-oss:20b`, fallback local `qwen2.5:7b`.**
Финально проверим на этапе 1 тест-кейсом «привет» + на этапе 2 — вызовом
тула `list_profiles`.

### Развилка 4: «активный профиль» (подстановка main'ом)

- **(A) Выделение ячейки = активный профиль** (клик по шапке ячейки уже
  выделяет её; добавить IPC `ui:selected-profile` → main). Слово `active`
  в тул-аргументе разрешается в него.
- **(B) Только явное имя/id в каждом вызове** — main не хранит выделение.

**Рекомендация: (A)** — «профиль, на который я смотрю» естественен для
пульта; (B) оставляем как поведение по умолчанию до конца этапа 1, если (A)
не одобрите.

## 6. Этап 3 — внесённые уточнения (реализовано)

Спецификация «RAG + search_faq + profileName в log_tail + фикс клампа»
реализована без эмбеддингов и внешних сервисов («RAG-lite»):

- **log_tail**: параметр `profileName` (имя/id/«active» — резолв через
  resolve.ts тем же порядком 1–4) → тул сам фильтрует строки по тегу
  `[<profileId>]` и добавляет 5 общих строк контекста (ошибки приложения,
  не привязанные к профилю, но важные для диагностики). Сигнатура:
  `log_tail(profileName?: string, lines?: number)` — `lines` по умолчанию
  30, максимум 50. Кламп 150 символов на КАЖДУЮ строку внутри тула, до
  склейки: 30 × 150 = 4,5 КБ — с запасом под общий лимит 8 КБ; глобальный
  кламп реестра не тронут (остаётся страховкой от раздувания других тулов).
- **search_faq**: грубый русский стеммер («крашится» → «краш»,
  «настроить» → «настро»), доменные синонимы («фингерпринт» ↔
  «отпечаток» ↔ «fingerprint», «куки» ↔ «cookies»), цитата выдаётся
  вокруг строки с максимумом совпадений, топ-3 вместо топ-2. Список
  документов прежний: README.md, BACKLOG.md, ROADMAP.md, docs/*.md.
- **README**: добавлен раздел «FAQ — короткие ответы» — 6 вопросов-
  заголовков (прокси, фингерпринт, краш, форматы прокси, расширения,
  cookies). Вопросы в разговорной форме совпадают с заголовками и
  стабильно занимают топ выдачи search_faq — до этого «крашится» в
  документации не встречалось (было «краш»), и keyword-поиск промахивался.
- **Системный промпт v3**: правило 8 — логи конкретного профиля
  запрашивать через log_tail с profileName (не грапать профиль из общего
  хвоста); «Как работать с тулами» — запросы к search_faq можно
  формулировать разговорными словами.

IPC-контракт и реестр тулов не менялись (сигнатура log_tail расширилась
опциональным profileName — для модели это обратно совместимо).

### Этап 3.1 — фиксы обратной связи после прогона

Три бага с живого ассистента (все — поведенческие, контракт IPC не тронут):

- **log_tail отдавал модели её же логи.** В кольцевом буфере есть строки
  `[assistant]` (внутренние логи LLM: chat started, тул готово/отказ,
  fallback-parser). Видя собственные ошибки, модель зацикливалась на их
  разборе. Фикс: фильтр `!message.includes('[assistant]')` стоит ДО
  level-фильтра и срезов — бюджет строк (30) тратится только на записи
  браузера/профилей, ни модель, ни карточка UI внутренних строк не видят.
- **Галлюцинации вместо документации.** На «как проверить фингерпринт»
  модель выдумывала несуществующие UI-кнопки. Фикс: системный промпт v4,
  правило 11 — вопросы «как/где/почему/что делать» о работе Brouser
  обязывают сначала вызвать search_faq; пустой результат = честный ответ
  «В документации Brouser нет ответа на этот вопрос»; выдумывать шаги,
  кнопки и настройки запрещено.
- **Дубли ответа после карточек.** set_layout показывал карточку
  «Раскладка изменена», затем модель писала то же текстом. Фикс двойной:
  правило 4 промпта v4 (после успеха меняющего тула — ровно одно слово
  «Готово»/«Сделано») + механическое подкрепление в агентском цикле:
  результат role:'tool' меняющихся тулов получает приписку «карточка уже
  показана — не дублируй» (ToolResult.mutating). Карточка log_tail в UI
  ужата до 3 строк × 100 символов (полный текст — только модели).

Тесты: smoke — промпт v4 (правила 4/11 дословно); integration — сценарий 4
(лог-буфер со строками [assistant]: фильтр в тексте для модели, в карточке
UI и в общем контексте) + проверка приписки в сценарии 3 (set_layout).
